## تفسير النتيجة

## أخطر إجراء يجب تجنبه

**لا تشغّل كل ملفات GitHub غير المطابقة على الإنتاج، ولا تعِد تهيئة migrations، ولا تستخدم reset.** قد تؤدي إعادة تطبيق SQL إلى تكرار تغييرات أو تغيير صلاحيات أو إتلاف بيانات أو تعطيل الطلبات.

## طريقة المصالحة الصحيحة

1. جلب أسماء/إصدارات الـ130 من سجل Supabase وتصديرها كما هي.
2. إنشاء جدول مقارنة لكل migration: اسم قاعدة البيانات، ملف GitHub المقابل، تطابق المحتوى (hash)، هل التغيير مدمج في ملف آخر، والجداول/RPC/policies التي يؤثر فيها.
3. مراجعة migrations ذات الأثر الأمني والمالي أولاً: RLS، RPC grants، wallet، coupons، subscriptions، payments، dispatch.
4. إعداد migrations تصالحية جديدة فقط عند وجود فرق فعلي مثبت، دون تعديل السجل القديم أو إعادة تطبيقه.
5. اختبار المصالحة في بيئة منفصلة/فرع تطوير قبل أي نشر.
6. بعد اكتمال المقارنة، اعتماد GitHub كمصدر وحيد للمستقبل مع توثيق نقطة البداية الحالية للإنتاج.

  - `refresh_driver_performance_tier_from_rating()` — مرتبطة بمشغل على `ratings`.
  - `refresh_driver_performance_tier_from_request()` — مرتبطة بمشغل على `service_requests`.
  هاتان الدالتان لا تقبلان معاملات وتستخدمان OLD/NEW الخاصة بالمشغل. الإجراء المقترح هو مراجعة ثم سحب EXECUTE من PUBLIC/anon/authenticated مع اختبار أن المشغلات تستمر بالعمل؛ لم يتم تنفيذ REVOKE أو أي DDL.
- **الأمان:** ظهر تحذير واحد عن `pg_net` في schema public، ويحتاج مراجعة توافق قبل نقله.

- دوال SECURITY DEFINER التي راجعناها للإدارة لم تكن قابلة للتنفيذ من `anon`، ووجدنا داخل الدوال الحساسة تحققاً من `auth.uid()` أو صلاحية الإدارة. لكن تحذير 103 دوال متاحة لـ`authenticated` لا يُحسم جماعياً؛ يجب تدقيق كل دالة حسب عقدها واستخدامها.

**قرار التنفيذ:** لا نطبق إصلاحات RLS أو grants أو extension schema على الإنتاج الآن؛ تسبقها مصالحة سجل migrations واختبارات staging، ثم migrations تصالحية صغيرة ومحددة.
