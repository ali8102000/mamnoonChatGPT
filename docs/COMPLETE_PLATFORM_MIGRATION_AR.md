# خطة نقل ممنون بالكامل إلى Supabase والاستقلال عن Lovable

الحالة: جرد معماري أولي، لا يمثل اكتمال النقل.
المشروع الخلفي المعتمد: `enteiolvirenbhkyskgb` (`mamnoon-new`).
المستودع: `ali8102000/mamnoonChatGPT`.
فرع العمل: `chore/decouple-lovable-backend`.

## القرار المعماري النهائي

- **GitHub**: المصدر الوحيد للكود، migrations، Edge Functions، إعدادات البناء والتوثيق.
- **Supabase**: المصدر الخلفي الوحيد للبيانات والحسابات والصلاحيات والملفات والعمليات الخلفية والإشعارات والجداول الزمنية والأسرار.
- **Web hosting**: استضافة مستقلة للواجهة فقط (Vercel حالياً مؤقتاً أو بديل مستقل بعد التحقق). لا تُخزن فيها مفاتيح خلفية ولا يعتمد التطبيق على Lovable.
- **Android**: تطبيق Expo/EAS يستهلك Supabase نفسه، ولا يتصل بقاعدة بيانات أو خدمة إدارية ثانية.
- **Lovable**: لا يبقى مصدراً للكود أو قاعدة بيانات أو مصادقة أو تشغيل أو أسرار. لا يُحذف المشروع القديم قبل إثبات الاستقلال الكامل.

Supabase لا يستضيف تطبيق TanStack Start/React كواجهة ويب عامة بحد ذاته؛ دوره الخلفية. لذلك لا نعد المستخدم بأن Supabase سيحل محل استضافة الواجهة.

## الجرد الفعلي للمشروع الخلفي

تمت قراءة المشروع النشط `enteiolvirenbhkyskgb`:
- الحالة: `ACTIVE_HEALTHY`.
- قاعدة البيانات: PostgreSQL 17.11.
- 60 جدولاً في schema `public`، وجميعها ظهر أن RLS مفعّل عليها.
- 4 Storage buckets.
- 130 migration مسجلة حتى `20261117113336`.
- 10 Edge Functions نشطة:
  - `admin-users` (v7, JWT verification on)
  - `admin-finance` (v3, JWT verification on)
  - `admin-governance` (v2, JWT verification on)
  - `admin-subscriptions` (v2, JWT verification on)
  - `auto-taxi-pricing` (v12, JWT verification on)
  - `zaincash-create-payment` (v4, JWT verification on)
  - `zaincash-config-status` (v2, JWT verification on)
  - `auth-proxy` (v2, JWT verification off)
  - `zaincash-callback` (v4, JWT verification off)
  - `zaincash-webhook` (v4, JWT verification off)

تعطيل JWT الافتراضي في `auth-proxy` وواجهات الدفع الراجعة/webhook ليس بالضرورة خطأ؛ يجب تدقيق بديل التحقق لكل endpoint (توقيع/سر/مصدر/منع replay) قبل أي تعديل.

| الصور والمرفقات | Supabase Storage | 4 buckets؛ مراجعة السياسات والملكية والروابط |

| مهام الخلفية والجدولة | Supabase Cron/Queues/Edge Functions | توجد جداول queue/outbox وpg_cron؛ يلزم مطابقة كل worker |
| التحليلات والتقارير | PostgreSQL/RPC/Edge Functions | جزء منها موجود؛ يلزم ربط الواجهات والتحقق |
| الويب | كود GitHub + استضافة مستقلة للواجهة | Vercel حالياً، ليس بديلاً عن Supabase |
| Android | Expo/EAS + Supabase | يلزم فحص EAS env/build وربط المرجع الصحيح |
| ملفات المصدر وعمليات النشر | GitHub | PR #168 غير مدموج بعد |
| إعدادات وأسرار الخدمات | Supabase Edge Function Secrets / Vault عند الحاجة | جرد الأسماء والقيم غير مكتمل؛ لا تُطبع أو تُنقل عشوائياً |

## خطة التنفيذ الإلزامية

### المرحلة 1 — تثبيت مصدر الحقيقة (قراءة فقط)
1. تثبيت مشروع Supabase الصحيح في كل إعدادات GitHub/Vercel/EAS.
2. جرد كل متغيرات البيئة في المستودع وVercel وEAS وSupabase بالاسم والتصنيف فقط.
3. تحديد أي خدمة خارجية مستخدمة فعلاً: Firebase، Google Maps/Places، Push provider، ZainCash، QiCard، بريد/OTP، وأي تخزين خارجي.
4. جرد كل الواجهات التي تستدعي Server Functions أو APIs أو SDKs مباشرة.
5. مطابقة migrations في GitHub مع الـ130 المسجلة في الإنتاج، وتحديد أي migrations مفقودة أو غير متطابقة قبل تطبيق أي شيء.

### المرحلة 2 — توحيد الخلفية
1. جعل Supabase Auth المرجع الوحيد للهوية والجلسات.
2. تحويل كل عمليات الإدارة والاشتراكات من Server Functions التي تستعمل Service Role إلى Edge Functions/RPC آمنة.
3. نقل منطق الطلبات والتسعير والدفع والإشعارات والموقع إلى وظائف Supabase حيث يلزم.
4. ضمان أن كل عملية تتحقق من JWT وهوية المستخدم والدور والقسم والنطاق الجغرافي في الخادم، وليس في الواجهة فقط.
5. الاحتفاظ بـRLS كحاجز قاعدة البيانات وعدم تعطيلها أو تجاوزها لمجرد سهولة النقل.

### المرحلة 3 — توحيد تطبيقات العميل
1. تحويل الويب وAndroid إلى نفس عقود API/Edge Functions.
2. إزالة الاتصالات الخلفية المكررة وأي اعتماد مباشر على Firebase/خدمات بديلة بعد إثبات عدم الحاجة لها.
3. توحيد مخططات المدخلات والمخرجات ورسائل الأخطاء.
4. الحفاظ على تطابق الواجهات والسلوك بين الويب والأندرويد.
5. التحقق من الخرائط والموقع المباشر والإشعارات والملفات والدفع على الجهاز الحقيقي.

### المرحلة 4 — الأسرار
1. تصنيف كل متغير: public أم server-only، والجهة التي تحتاجه.
2. وضع الأسرار الخادمية في Supabase Edge Function Secrets أو Vault بحسب نوع الاستخدام.
3. إبقاء Supabase URL وPublishable/Anon key فقط ضمن إعدادات العميل إذا كانت سياساتها آمنة.
4. منع Service Role وJWT secret وZainCash secret ومفاتيح الخادم من `VITE_*` و`EXPO_PUBLIC_*`.
5. لا تحذف متغيرات Vercel/EAS قبل نقل جميع المستهلكين واختبار الإنتاج.
6. تدوير الأسرار التي قد تكون تعرضت للكشف وفق خطة مدروسة، لا بشكل يقطع الخدمة.

### المرحلة 5 — الاختبار والإطلاق
- اختبار أدوار: زبون، سائق، فني، دعم، مالية، عمليات، مراقبة، مدير قسم، مدير عام، مدير أعلى.
- اختبار نطاق المحافظة والنطاق العام.
- اختبار التسجيل والدخول وتغيير الرقم واستعادة الحساب.
- اختبار إنشاء الطلب، القبول، التتبع، الإلغاء، الإكمال، الدفع، الاسترداد.
- اختبار الصور والمرفقات والدردشة والإشعارات.
- اختبار الإدارة والمالية والاشتراكات والحوكمة.
- بناء Web وAndroid وإجراء اختبارات تشغيل حقيقية.
- تشغيل فترة تحقق دون تعطيل النظام القديم.
- بعد اجتياز الاختبارات فقط: دمج PR، النشر، نقل DNS إن لزم، ثم إزالة الأسرار/الخدمات القديمة وإغلاق اعتماد Lovable.

## ضوابط لا يجوز تجاوزها

- لا حذف بيانات أو جداول أو سياسات أو migrations.
- لا bulk revoke لصلاحيات RPC أو RLS.
- لا تدوير أسرار الدفع أو Auth دون خطة تحقق.
- لا تغيير DNS أو إيقاف Lovable أو نقل ملكية الاستضافة قبل اختبار البديل.
- لا نشر Edge Functions أو migrations غير مفحوصة إلى الإنتاج.
- لا إعلان أن النقل اكتمل لمجرد وجود الجداول أو الوظائف؛ يجب إثبات أن كل شاشة ومسار فعلي يستخدم الخلفية الجديدة.

## ما لم يثبت بعد

- لا يوجد حتى الآن إثبات أن Firebase غير مستخدم في runtime؛ حزمة `firebase` ما زالت ضمن `package.json`.
- حزمتا `@lovable.dev/ai-gateway` و`@lovable.dev/vite-tanstack-config` ما زالتا ضمن `package.json`. لا تحذفان قبل فحص imports والـlockfile والبناء.
- لا يوجد جرد موثق كامل لأسماء أسرار Supabase Edge Functions وEAS.
- لا يوجد تأكيد بأن جميع migrations الـ130 موجودة ومتطابقة في GitHub.
- فحوص Vercel للـPR متوقفة حالياً بسبب `build-rate-limit`، فلا يمكن اعتمادها كاختبار ناجح.
- PR #168 ما زال Draft وغير مدموج.

## آخر حالة آمنة

هذه الوثيقة جرد وخطة فقط. لم تُغيّر قاعدة البيانات أو Auth أو RLS أو Storage أو الأسرار أو DNS، ولم تُنشر وظائف جديدة، ولم يُدمج PR. النقل الكامل عملية مرحلية لا يمكن اعتبارها منجزة قبل اجتياز الاختبارات أعلاه.
