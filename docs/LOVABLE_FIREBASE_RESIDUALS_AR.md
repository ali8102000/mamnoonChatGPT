## 1. اعتماد Lovable الموجود في مسارات المصدر

### المصادقة وحساب المدير الأعلى
- أصبح تحديد صفة المدير الأعلى من نتيجة RPC `is_super_admin` المرتبطة بالمستخدم المصادق عليه، وليس من مقارنة بريد إلكتروني ثابت أثناء التسجيل.
- تم توحيد إنشاء البريد الداخلي للحساب في العميل و`auth-proxy`: يستخدم البريد الذي أدخله المستخدم إذا وفره، وإلا ينشأ بريد داخلي مرتبط برقم الهاتف.
- لا يزال هذا التغيير بحاجة إلى اختبار تسجيل حساب جديد برقم هاتف فقط، وبرقم هاتف مع بريد تواصل، وتسجيل دخول مدير أعلى/مستخدم عادي قبل نشره.


### جلسات المصادقة في المعاينة
- حُذف الملف `src/integrations/supabase/previewAuthStorage.ts` الذي كان يمرر جلسات الدخول إلى محرر Lovable عبر `postMessage`.
- أزيل استدعاء `brokeredPreviewStorage()` من `src/integrations/supabase/client.ts`، وأصبح عميل الويب يستخدم آلية تخزين Supabase الافتراضية في المتصفح.
- أزيلت رسالة الخطأ التي كانت تطلب ربط Supabase داخل Lovable.

المتبقي: يجب اختبار تسجيل الدخول، إعادة فتح الصفحة، تحديث الجلسة، وتسجيل الخروج في الويب المستقل؛ لا نعلن نجاح هذا المسار قبل اختبار فعلي.

### تقارير الأخطاء
- حُذف `src/lib/lovable-error-reporting.ts` وأزيل استدعاؤه من `src/routes/__root.tsx`.
- أخطاء React ما زالت تظهر في سجل المتصفح عبر `console.error` وتظهر للمستخدم في شاشة الخطأ، لكن لا يوجد حالياً نظام مركزي مستقل لمراقبتها.
- الخطوة التالية: اختيار نظام مراقبة مستقل وتنقيح بياناته قبل الإرسال؛ لا نرسل رموز جلسات أو أرقام هواتف أو stack traces خام إلى جدول عام.

### الحزم وإعداد البناء
- أزيلت `@lovable.dev/vite-tanstack-config` و`@lovable.dev/ai-gateway` من `package.json` و`bun.lock`.
- إعداد البناء الحالي يستخدم TanStack Start وVite وNitro مباشرة، ولا يستورد إعداد Vite من Lovable.
- نُقلت ميزة مساعد استيراد CSV إلى `supabase/functions/import-assist`، وأصبح العميل يستدعيها عبر Supabase Edge Functions.
- وظيفة الذكاء الاصطناعي تقبل إعداد مزود OpenAI-compatible من أسرار Supabase (`AI_API_KEY`, `AI_MODEL`, واختيارياً `AI_BASE_URL`) وتعود إلى المطابقة التقريبية إذا لم تتوفر هذه الإعدادات.
- نجحت فحوص CI على الالتزام `b391c40`: فحوص الويب، وDeno لوظائف Edge، وExpo/Android، وفحص تكامل صور الخدمات، والتحقق الشامل. هذا يثبت جودة البناء والأنواع والاختبارات المعلنة، ولا يثبت تكافؤ عقود الوظائف الحية أو اختبار تشغيل كامل.

## 2. اعتماد Firebase الموجود في المصدر

`package.json` يحتوي حزمة `firebase`، و`src/lib/firebase.ts` يهيئ Firebase عبر متغيرات `VITE_FIREBASE_*`، ويحتوي وظائف:
- Firebase Analytics.
- Firebase Performance traces.
- Firebase Cloud Messaging (FCM): طلب الإذن، استخراج FCM token، واستقبال رسائل foreground.

الأثر: هناك اعتماد حقيقي في المصدر على Firebase للإشعارات والتحليلات وقياس الأداء. هذا لا يعني أن Firebase هو قاعدة البيانات أو نظام تسجيل الدخول؛ لكن لا يمكن إعلان إزالة Firebase بالكامل قبل تتبع كل مستوردي `src/lib/firebase.ts` ومصدر تسجيل/تحديث/حذف FCM tokens، وكذلك وجود service worker وملف إعداد FCM للخادم.

قرار الترحيل:
- **قاعدة البيانات والهوية والملفات والإدارة**: Supabase.
- **Push notifications**: Supabase Edge Functions تكون مصدر قرار الإرسال وتخزين التوكنات، لكن خدمة توصيل الإشعارات نفسها تحتاج مزوداً مثل Expo Push أو FCM/APNs. Supabase لا يحل محل شبكات توصيل إشعارات Android/iOS تلقائياً.
- **Analytics/Performance**: إما إزالة القياس غير الضروري أو اختيار بديل مستقل بعد تحديد التقارير التي تعتمد عليه. لا نستبدله بمخزن PostgreSQL خام دون سياسة خصوصية واحتفاظ وتنقيح.

## 3. إعدادات العميل

`config/public-backend.json` يحتوي عنوان Supabase ومفتاح Publishable عام. هذا ليس مفتاح Service Role، ولا ينبغي معاملته كسر. تبقى صلاحية الوصول محكومة بـRLS وEdge Functions.
`src/integrations/supabase/client.ts` يقرأ أيضاً `SUPABASE_URL` و`SUPABASE_PUBLISHABLE_KEY` للخادم. يجب التأكد من أن قيم العميل العامة تطابق مشروع Supabase الصحيح في الويب وEAS.

## 4. أعمال مطلوبة قبل الإزالة

1. تتبع كل imports واستدعاءات `firebase.ts` في كامل المستودع، بما فيها web service worker وnative push.
2. تحديد هل تطبيق Android يستخدم Expo Notifications أو FCM مباشرة، وتوحيد مسار التوكنات.
3. بناء Edge Function لإرسال الإشعارات مع تحقق صلاحيات ومنع إساءة الاستخدام، وربط مزود push مناسب.
4. اختبار تخزين Supabase Auth الافتراضي بعد حذف Lovable preview storage، بما يشمل استعادة الجلسة وتحديثها وتسجيل الخروج.
5. اختيار مراقبة أخطاء مستقلة واختبار تنقيح البيانات قبل إرسال أي تقارير.
6. حذف حزم Lovable بعد التأكد من عدم وجود imports/transforms تعتمد عليها.
7. حذف Firebase من `package.json` ومتغيرات البيئة فقط بعد التأكد أن كل الاستعمالات انتقلت وأن push/analytics/performance لم تتعطل.

## 6. نقل الخرائط إلى Supabase — الحالة الحالية

تم تنفيذ النقل الأولي في هذا الفرع:
- أُنشئت Edge Function باسم `maps-proxy` ونُشرت في Supabase بحالة `ACTIVE` والإصدار 2 و`verify_jwt=true`.
- الويب في `src/lib/maps.functions.ts` وAndroid في `expo-app/src/lib/maps-api.ts` يستدعيان `supabase.functions.invoke("maps-proxy")` مباشرة.
- وظيفة البحث تستخدم Supabase RPC والتخزين المؤقت، وPhoton/OpenStreetMap للنتائج الجديدة، مع فلترة هندسية بحدود المحافظات.
- تفاصيل الأماكن المحفوظة، reverse geocoding، اكتشاف المحافظة، التحقق من حدودها، ومسار الطريق أصبحت داخل الوظيفة.
- تمت إزالة المفتاح القديم المضمّن من `src/lib/google-maps.ts`، وإزالة متغيرات Lovable Maps القديمة من عميل الويب.
- مسار Vercel القديم `/api/mobile-maps` لم يُحذف بعد؛ أصبح جسر توافق مؤقتاً يمرر الطلب إلى Supabase فقط، دون منطق خرائط أو اتصال بـLovable أو استخدام Service Role.
- تم رفض action القديم `createTaxiRequest` داخل الوظيفة الجديدة برمز 410؛ إنشاء التاكسي العادي يمر عبر `auto-taxi-pricing` كما كان في الويب وAndroid.

**حدود ما تم إثباته:** فُحصت مراكز المحافظات الـ18 ووقعت كلها داخل مضلعاتها في GeoJSON، لكن لم يكتمل بعد اختبار حي مصادق عليه من جلسة مستخدم حقيقية على الويب وAndroid.

## 7. مسار إنشاء طلب التاكسي

- الويب وAndroid يستخدمان Edge Function `auto-taxi-pricing` للعرض السعري وإنشاء طلبات التاكسي العادية.
- إنشاء طلبات المركبات الكبيرة (باص/كيا حمل/كيا ركاب) ما زال مساراً منفصلاً عبر `service_requests` وله Triggers وقواعد مختلفة؛ لا نغيّره ضمن نقل الخرائط.
- جسر Vercel القديم لم يعد ينشئ طلبات؛ يمرر فقط إلى `maps-proxy`.
- `maps-proxy` يرفض `createTaxiRequest` القديم حتى لا يتجاوز تسعير التاكسي والكوبونات والتحقق الخلفي.
